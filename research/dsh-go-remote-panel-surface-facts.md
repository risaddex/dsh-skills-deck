## Presentation routes today

- **Web slot / Web island:** web plugins register React slot occupants; DSH Go's seam design prefers a native adapter and otherwise uses an island containing the official web client. The deck's `sidebar.right.pane.tab` is a recognized conversation-specific entry, not a Flutter/native protocol declaration. Sources: G `docs/design/plugin-seams.md:9-12,21-24`; G `docs/plugins/web-panels.md:3-9`; D `src/client/panelAssembly.ts:165-178`.
- **Native `dshGo` panel:** package manifest declares contributions, host-side `ctx.dshGo.panel(id, {view,data,actions})` supplies declarative views/data and handlers, and the App consumes contributions, views, a multiplexed subscription WebSocket and invoke. This is a separate API, not execution of the plugin's React client. Sources: G `docs/design/native-plugins-protocol.md:14-21,139-161,310-312,340-340`.
- **Tool card:** a tool's `presentationMeta` returns `{ 'dsh-go/view': view }`; that metadata travels in the conversation record. The App parses only successful calls with that meta key, using its tool-card budget. It needs no panel manifest. Sources: G `docs/plugins/quickstart.md:29-51`; G `docs/plugins/slots.md:12-12`; G `app/lib/ui/chat/tool_view.dart:13-20`; G `app/lib/ui/chat/dsh_ui/dsh_ui_plugin.dart:10-19`.
- **`dsh-ui` fenced reply:** model-generated JSON in an assistant message renders as native cards; it is not a persistent plugin panel. Options/confirm send a message back to the model, unlike plugin view actions that invoke plugin handlers. Sources: G `docs/plugins/native-for-free.md:28-36`; G `app/lib/ui/chat/render/markdown_body.dart:472-482`.

## What survives the relay

- **Tool cards and `dsh-ui` remain presentation options**, because they are conversation content, not extra HTTP routes. The host coverage table explicitly allows relay tool cards and disallows native panels and islands; the native-for-free table lists both message fences and metadata cards for all hosts. The tunnel allow-list includes `session/follow` and `session/page` (the host does too). This establishes supported routing, not a promise that every historic record contains metadata or every view/action works. Sources: G `docs/plugins/hosts.md:3-9`; G `docs/plugins/native-for-free.md:5-12`; G `packages/dsh_remote/lib/src/carrier/tunnel_carrier.dart:62-72`; R `dist/harness-remote-bridge.js:128-133`.
- **No web page/island fallback over this carrier:** `canReadWebBoot` is true only for `DshHttpCarrier`; both web boot and bridge inventory providers return null when false, and seat inventory receives that reachability flag. Docs explicitly hide web-only panels on relay hosts. Sources: G `packages/dsh_client/lib/src/client_inventory_api.dart:479-487`; G `app/lib/plugins/seams/seat_state.dart:27-51,57-69`; G `docs/plugins/web-panels.md:78-82`; G `docs/design/plugin-seams.md:226-226`.
- **No native bridge over this carrier:** `nativeBridgeProvider` returns null without `client.canReachDshGo`; the latter is the concrete HTTP-carrier type check. Calling the API directly does not bypass that: `_dshGoConnection` throws `dsh-go/unsupported` for non-HTTP carriers. Assets are HTTP-only too. Sources: G `app/lib/plugins/native/native_state.dart:121-139`; G `packages/dsh_client/lib/src/dsh_go_api.dart:686-688,878-883`.
- **Remote is not a transparent HTTP/WebSocket proxy.** `DshCarrier` exposes unary endpoint calls and mux links; its contract anticipates a fixed remote endpoint allow-list. `TunnelCarrier` maps these to `harness.remote.call`, stream open/close and tunnel events, checks its own allow-list, and explicitly rejects stream uplink/half-close. Sources: G `packages/dsh_client/lib/src/carrier.dart:3-17,33-75`; G `packages/dsh_remote/lib/src/carrier/tunnel_carrier.dart:4-7,21-24,247-247,450-470,944-960,993-1007`.
- **The installed Remote host forwards official allow-listed Gateway operations plus a narrow plugin POST facility, not arbitrary plugin UI.** Its official endpoint list and enforcement are in R `dist/harness-remote-bridge.js:73-180,230-231,699-700`. `service.js` constructs the plugin bridge only when a dispatcher exists and advertises `plugin.route.v1`; the RPC router dispatches `plugin.route.call` to it. Sources: R `dist/service.js:132-141,503-510`; R `dist/rpc-router.js:309-309,348-350`.
- **Neither `/dsh-go/*` nor an equivalent native-panel route is admitted.** The entire plugin-route list is `api/bot` and `api/session/uploadFileBinary`; the former has a strict DS Bot endpoint/payload schema and the latter an image/file intake schema. Unknown inputs fail validation. The returned transport shape is `{status,json}`, bounded in size and time; it is not a GET/WS forwarding contract. The browser-side adapter intercepts only POST to `api/bot`, checks `remoteFeatures.pluginRoute`, and sends `plugin.route`. Sources: R `dist/plugin-route-bridge.d.ts:3-15`; R `dist/plugin-route-bridge.js:4-5,46-76,85-104,113-121`; R `dist/plugin-route-client.js:109-109,157-175`. Thus the existence of plugin-route forwarding is **not** evidence of native-panel forwarding (inference from those exact schemas).
- **Host identity is not transport parity:** Remote's README says DSH Go can connect through the plugin, but does not promise plugin UI forwarding. The Go guide distinguishes SSH's forwarded local HTTP port from Remote's encrypted LAN/P2P/TURN/relay connection and says DSH Web does not open over Remote. Sources: R `README.md:7-9`; G `docs/guide/en/03-engine-hosts.md:100-109,117-134`. Plugin management is another independent capability: the guide permits enable/disable over Remote, not in-app install/uninstall. Source: G `docs/guide/en/08-plugins.md:25-35`.

## Why this deck does not appear

- **Its “native right sidebar” terminology means the DSH web shell's right sidebar, not DSH Go's native protocol.** It obtains `sidebarRightTabs`, registers a type and guide entry, then mounts `DeckSidebarTab`/`DeckNativeTabTitle` in keyed web slots. Opening calls `sidebarRight.openTabIn` or `openTab`, returning false if the controller is missing. Sources: D `src/client/panelAssembly.ts:148-178`; D `src/client/kernel/router.ts:130-145`.
- **Manifest and tool registration do not supply the other surfaces:** the complete inspected package manifest has no top-level `dshGo`, and declares `dsh.client.platform: "web"`. Both tool registration branches construct descriptors with name, description, parameters, timeout, output and execute, but no `presentationMeta`. A literal search of D `src/` and `package/` (excluding node_modules) also found no `presentationMeta`. Sources: D `package/package.json:1-80` (web declaration at 72-76); D `src/deck/registration/register-options.ts:377-410`. This is absence in the inspected source, not a claim that ordinary deck tool results cannot be displayed as generic tool rows; G explicitly supports those: `docs/plugins/native-for-free.md:10-18`.
- **Adding `dshGo` + `ctx.dshGo.panel` alone does not fix relay access.** It would define a new native representation only on a host with the bridge loaded in the relevant DSH instance/profile, with a valid enabled manifest and a registered or static view. It cannot make the App's non-HTTP carrier pass its type checks or extend Remote's route/schema allow-lists. Use conditional `ctx.inject(['dshGo'], ...)`, not a mandatory top-level dependency; the protocol says absent bridge leaves that callback suspended. Sources: G `docs/design/native-plugins-protocol.md:145-153,310-312,340-340`; G `packages/dsh_client/lib/src/dsh_go_api.dart:686-688,878-883`; R `dist/plugin-route-bridge.js:4-5,49-70`. The insufficiency is an inference directly from these independent gates.

## Smallest credible changes and alternatives (proposals, not existing support)

- **Smallest relay-native panel approach (inference):** implement a bounded native deck view + host data/action handlers in **dsh-skills-deck**; ensure **dsh-go**'s host bridge is installed on the connected host. Add a negotiated, scoped, bounded native-plugin tunnel contract in **ds-harness-remote** for contributions, view reads and invokes, and implement its matching transport in **dsh-go** (`NativeBridge`/client API), replacing concrete HTTP-only eligibility with negotiated capability checks. A deliberately non-live, manually refreshed first panel could avoid streaming and images, but must explicitly define refresh/staleness semantics rather than claim live protocol parity. Dependencies: G `app/lib/plugins/native/native_state.dart:85-118,134-139`; G `docs/design/native-plugins-protocol.md:14-21,161-161`; R `dist/plugin-route-bridge.js:49-76,85-121`. Merely adding `/dsh-go/` to a string list is insufficient: the existing request body is DS-Bot-specific, lacks HTTP methods and subscriptions, and the Go API still requires HTTP.
- **Full native protocol alternative (inference):** provide authenticated native read/invoke plus bidirectional subscription semantics, reconnect/resync and invalidation; implement asset transport only if needed. This can be a dedicated tunnel RPC family, or official typed Gateway endpoints with changes to both host and Dart endpoint allow-lists and an adapter in the host bridge. No such native family is present in the inspected allow-lists. Preserve scope, capability negotiation, effect validation and authentication rather than opening arbitrary routes. Sources defining the required behavior: G `docs/design/native-plugins-protocol.md:14-21,211-211,317-319,395-420`; G `packages/dsh_client/lib/src/carrier.dart:50-64`; G `packages/dsh_remote/lib/src/carrier/tunnel_carrier.dart:21-24,1004-1007`; R `dist/harness-remote-bridge.js:699-700`.
- **Larger web alternative (inference):** a secured web/assets/WebSocket tunnel plus Go web reachability, inventory and island-policy integration would be needed to carry the existing React panel; native-panel forwarding alone does not carry it. Island policy also currently requires the phone's local engine for the documented surfaces, so HTTP reachability alone must not be treated as sufficient. Sources: G `docs/plugins/web-panels.md:16-16,29-29,57-57,78-82`; G `app/lib/plugins/seams/seat_state.dart:27-69`; D `src/client/panelAssembly.ts:165-171`.
- **Smaller non-panel workaround (inference):** add safe tool-card metadata to deck tool descriptors or teach a skill to emit supported `dsh-ui` summaries. This uses the existing conversation route and needs no new relay panel transport, but supplies a snapshot/result, not the current sidebar or a general plugin invoke channel. Sources: D `src/deck/registration/register-options.ts:386-407`; G `docs/plugins/quickstart.md:29-51`; G `docs/plugins/native-for-free.md:28-36`.
- **Different connection, not a relay fix:** SSH attach-only forwards the host's DSH HTTP port, which meets the Go client API's carrier model; native plugin bridge installation remains a separate prerequisite. The older coverage table calls SSH bridge installation “phase two,” so do not infer working SSH native panels merely from transport eligibility. Sources: G `docs/guide/en/03-engine-hosts.md:105-109`; G `packages/dsh_client/lib/src/dsh_go_api.dart:686-688`; G `docs/plugins/hosts.md:7-9`.

## Decisions settled (2026-11-23)

The maintainer settled the following after the investigation above. These are decisions, not findings from the inspected checkouts.

- **Scope:** a read-only deck panel. No create, update, close or prompt-injection actions.
- **Connection:** the panel must work through the current DSH Remote relay setup.
- **Placement:** one panel in the conversation details' Plugins tab (`session.tab`), scoped to that conversation's workspace.
- **Content:** the open map/spec tree with child tickets and blockers, plus a structured ticket detail opened on demand.
- **Freshness:** no cache between interactions and no polling. Opening the panel reads the tree; opening a ticket reads that ticket; the refresh button reads the tree again.
- **Transport:** one narrow deck-only read channel, not the general DSH Go native-panel protocol and not a generic HTTP/WebSocket tunnel. The negotiated feature is `deck.panel.read.v1`, with exactly two operations: `tree` and `ticket`.
- **Payloads:** `tree` returns a bounded thin tree of open containers and their child tickets; `ticket` returns title, state, labels, body, acceptance criteria, progress and blockers. Comments are out of scope.
- **Bounds:** at most 50 containers and 200 tickets in the tree; truncation is shown in the panel instead of being silent.
- **Failure:** a tree failure replaces the content with an error and a retry action; a ticket failure stays inside the detail and keeps the loaded tree.
- **Compatibility:** old hosts without `deck.panel.read.v1` simply do not show the panel. No empty screen, error row or tool-card fallback in this MVP.
- **Backends:** GitHub, GitLab, local Markdown and Linear, read through the existing tracker contract.
- **Acceptance:** an end-to-end run on a real Android device through the DSH Remote relay, against a real host, reading both the tree and a ticket.
- **Release order:** deck first exposes the read endpoints without changing its web UI; `ds-harness-remote` then forwards that channel and announces the feature only when the endpoints exist; DSH Go last shows the panel. Each step remains compatible with the older versions of the other two.
- **Spec shape:** one spec in `dsh-skills-deck` that states the contract and the three workstreams, with `dsh-go` and `ds-harness-remote` listed as external implementation dependencies.

- **Spec:** the settled implementation spec is issue #70 in `dsh-skills-deck`.
